# 注册流程验证与问题归因标准

本文档是本项目注册任务、资格检测、账号测活、分类流转和问题归因的统一标准。实现、测试、前端展示、数据库状态和人工分析必须遵守同一口径。

## 1. 核心结论

1. 新注册账号在数分钟后返回 HTTP 401，按本项目业务定义视为账号失活（死号）。
2. 新注册账号集中出现延迟 401，问题归属前置注册流程或其注册环境链路。排查必须从注册入口到账号创建完成这一段开始。
3. 密码设置、2FA、支付检测、提炼属于注册完成后的流程。它们可以暴露账号已经不可用，但未经严格对照实验，不得被认定为本次延迟 401 的根因。
4. 注册结束瞬间 AT 返回 HTTP 200，只能证明该时刻令牌可用，不能证明账号已经稳定注册成功。
5. 有试用资格是本项目注册成功的必要条件。没有试用资格、资格未知或资格检测失败，都不能进入支付方式检测及后续成功分类。
6. 本项目每个注册任务使用不同邮箱后缀、全新指纹和全新代理环境。在这些隔离条件真实成立时，并发本身不得被列为延迟 401 的原因。

## 2. 注册主流程边界

前置注册流程从创建分裂邮箱开始，到账号稳定性验证通过为止，包括：

1. 按用户已保存的邮箱后缀创建分裂邮箱。
2. 按用户已保存的入口分支、浏览器引擎、指纹和代理池创建任务。
3. 在真实浏览器上下文或所选协议分支中进入注册入口。
4. 完成邮箱提交、授权跳转、验证码发送和验证码校验。
5. 完成账号资料页和账号创建。
6. 获取会话及 AT。
7. 检测试用资格。
8. 对新账号执行延迟稳定性测活。

密码设置、2FA、支付方式检测和提炼不属于上述前置注册流程。排查注册问题时默认关闭这些步骤，避免扩大变量，但关闭它们不等于已经找到 401 的原因。

## 3. 成功判定

单个账号只有同时满足以下条件，才可标记为“注册成功”：

- OTP 的发送、收取和校验均有真实响应证据。
- 账号创建接口或页面完成状态有真实响应证据。
- 会话和 AT 来自该次注册上下文，不能从其他任务补入。
- `accounts/check` 或等价正式测活请求返回 HTTP 200。
- 资格检测明确返回 `eligible`。
- 延迟稳定性测活通过，未出现 401。

以下情况都不是注册成功：

- 只完成点击或页面跳转。
- 只拿到 OTP。
- 只在注册完成瞬间拿到 AT。
- 资格为 `unknown`、`not_eligible` 或检测失败。
- 注册后数分钟变为 401。
- 提炼或支付接口因账号状态返回 400/401。

## 4. 延迟测活标准

每批验证至少使用 5 个当天新注册账号，不能用单个样本推断整体结果。每个账号至少记录以下三个时间窗口：

- T+0：刚获取 AT 后的即时检测，仅作基线。
- T+5 至 T+10 分钟：第一次延迟检测。
- T+20 至 T+30 分钟：稳定性确认。

最后一个时间窗口未通过，整条注册任务按注册失败处理。测试期间的 401 账号默认保留，不自动删除，以便对比其 HAR、响应体、任务事件和环境快照。

401 的固定解释：

- 新账号：前置注册流程或注册环境导致账号失活。
- 已长期存活账号：才允许进一步区分封号、套餐状态变化或账号状态迁移。
- 不得把新账号 401 描述为普通 AT 过期、测活偶发失败或提炼故障。

## 5. 资格与分类状态机

分类必须由数据库唯一状态生成，前端不得自行推断或保留过期分类。

| 条件 | 应进入的分类 | 禁止进入 |
| --- | --- | --- |
| 分裂邮箱已创建、任务未运行 | 准备阶段 | 注册中及后续分类 |
| 注册主流程运行中 | 注册中 | 支付方式待定、提炼 |
| 流程异常或延迟 401 | 待修复/注册失败 | 支付方式待定、提炼 |
| AT 有效但资格未知 | 测资格 | 支付方式待定、提炼 |
| 明确无试用资格 | 无试用失败处理 | 支付方式待定、提炼 |
| 有试用资格且延迟测活通过 | 支付方式待定 | 直接标记提炼完成 |
| 支付能力检测真实完成且成功 | 提炼或对应支付分类 | 仅因任务结束就进入提炼 |

后缀统计必须分开：

- 连续 OTP 最终超时只累计“无验证码黑名单”。
- 连续三次明确 `not_eligible` 只累计“无试用黑名单”。
- 401 属于注册失败，不得累计为无验证码或无试用。

## 6. 配置执行标准

1. 前端保存值、服务端持久化值、任务快照和实际执行值必须一致。
2. 每个配置只能有一个权威开关，不允许两套开关分别控制同一行为。
3. 总开关关闭时，其所有子步骤必须停止执行；不能读取残留子开关绕过总开关。
4. 任务创建时必须固化并展示实际值：执行类型、实现分支、适用的指纹浏览器、代理池、指纹、附加步骤和并发参数。
5. 禁止静默改为直连、服务默认、其他代理池、711 中继、其他分支或其他浏览器。
6. 用户上次明确选择的配置必须持久化并在下次任务中复用，除非用户主动修改。
7. 失败时应明确终止并报告冲突配置，不得用兜底路径掩盖配置错误。

执行配置分为两层，不能混用：

- 一级执行类型只有“浏览器”“半协议”“协议”。
- “浏览器”使用真实指纹浏览器完成页面操作；当前唯一实现为 `flowpilot`。历史 `direct` 值统一迁移到 `flowpilot`，退役数字 ID 不得复用。
- “半协议”先由指纹浏览器加载真实上下文，再由实现明确规定哪些阶段复用上下文直连接口、哪些阶段保留页面操作；当前实现为 `context_protocol`。
- “协议”不启动指纹浏览器；当前唯一注册实现为 `freepp`；显式请求旧 HAR 实现返回错误。
- 浏览器和半协议类型必须显示并固化“指纹浏览器”配置；协议类型必须隐藏该配置，并在任务记录中标记为不适用。
- 执行类型、实现和指纹浏览器选项由服务端中央注册表下发。数字 ID 是稳定配置标识，内部 key 是持久化与执行标识，数组顺序不能作为标识。
- “实现列表”只登记可选处理器，不包含点击、OTP 或资料提交等步骤；具体步骤仍归各实现处理器所有。

## 7. 真实用户模拟标准

回归验证必须从前端按真实用户顺序执行：

1. 打开主邮箱会话。
2. 在前端显式选择后缀并创建分裂邮箱。
3. 核对前端显示的入口、浏览器和代理配置。
4. 点击启动。
5. 观察任务进入准备、注册和资格阶段。
6. 逐步核对页面 DOM、网络响应和数据库状态。
7. 完成延迟测活后再核对最终分类。

脚本和接口可用于读取证据、对账及定位实现，但不能代替前端用户模拟作为最终验收。

浏览器分支必须由真实页面状态推进：

- 点击后必须观察到对应网络请求或合法下一页面。
- 页面未出现目标表单时不能盲目点击、主动 `fetch` 或伪造状态。
- 必须等待关键资源和真实响应完成后再执行下一步。
- 直接页面内 `fetch`、人工补状态或绕过自然授权链，不算纯浏览器模拟。

## 8. HAR 与响应证据

每次分析必须把同一次抓包的 `.har` 与 `.responses.jsonl` 配对使用。单独查看 HAR 不足以判断完整流程。

对比至少覆盖：

- 请求顺序、方法、状态码和跳转链。
- 请求体、响应体和关键动态字段。
- Cookie 与 URL 中 `oai-did` 的一致性。
- `auth_session_logging_id`、`oai-sc`、Sentinel 状态的生成和更新时机。
- 代理/IP、地区、时区、语言、UA、Client Hints、TLS/浏览器版本的一致性。
- OTP 发送是否真实触发，不能仅凭开始轮询推断已发送。
- 账号创建、AT 获取和资格响应是否属于同一注册上下文。

本地成功样本 `D:\Desktop\指纹` 下的 HAR 和同名响应文件是基准证据；旧项目 `D:\Desktop\指纹\sign-up\turb-gpt-free-register` 只作为实现参考，不能覆盖真实抓包结论。

## 9. 401 根因排查顺序

出现新账号延迟 401 时，按以下顺序排查前置注册流程：

1. 注册入口是否与人工成功流程一致。
2. 授权请求链是否完整，是否存在跳步、主动补请求或响应门槛缺失。
3. 同一任务内代理/IP 是否保持必要的一致性。
4. 指纹、浏览器版本、UA、Client Hints、语言、时区和屏幕参数是否自洽。
5. `oai-did`、`oai-sc`、Sentinel 和授权会话字段是否在正确上下文中动态生成。
6. OTP 发送、验证、资料提交和账号创建的请求顺序及间隔是否符合人工成功样本。
7. 验证任务隔离是否真实成立：只有抓到跨任务复用设备标识、Cookie、会话对象或 Sentinel 状态的证据，才能认定为隔离失效；不得笼统归因于并发数量。
8. 同一指纹、同一代理或同一后缀的连续注册是否形成风控特征。

只有完成受控对照实验后，才能把某个变量列为根因。一次成功、一次失败或时间上的先后关系都不能单独证明因果。

## 10. 报告格式

每批测试必须报告：

- 创建任务数、完成注册数、OTP 失败数。
- 有试用、无试用、资格未知的数量。
- T+0、T+5 至 T+10、T+20 至 T+30 的 AT 状态。
- 401 数量和对应任务 ID。
- 每个任务的实际分支、浏览器、指纹、代理，以及任务间隔离是否真实成立。
- 最终数据库分类以及前端显示是否一致。
- 已确认事实、合理怀疑和尚未验证项，三者必须分开写。

不得用“任务 completed”“进入下一个分类”或“即时 AT 200”代替最终成功结论。
